Database Schema & RLS Policies

DB Schema — v1.0 · Supabase PostgreSQL
Date: June 2026 Owner: Akshay Rohilla Status: Live
Access model: Backend uses the service role key — bypasses RLS entirely. RLS policies protect against anyone using a user JWT to query Supabase directly, bypassing the API. All writes from the backend are safe by design.

Table Schemas

credits

One row per user. Tracks current balance and lifetime stats. Written by backend service role only.

ColumnTypeNotes

RLS Policies

Secure (per-user isolation)

applications — 4 policies (SELECT, INSERT, UPDATE, DELETE)
USING (auth.uid() = user_id)
credits — SELECT only
USING (auth.uid() = user_id) · Writes only via service role
cv_profiles — ALL operations
USING (auth.uid() = user_id)
cv_tailoring_log — ALL operations
USING (auth.uid() = user_id)
jd_evaluations — ALL operations
USING (auth.uid() = user_id)
payment_log — SELECT only
USING (auth.uid() = user_id) · Writes only via service role
usage_log — SELECT only
USING (auth.uid() = user_id) · Writes only via service role

Authenticated users only (Recruiter legacy tables)

jd_analyses — authenticated users only
TO authenticated USING (true) · No per-user isolation — admin only in practice
shortlist — authenticated users only
TO authenticated USING (true) · No per-user isolation — admin only in practice

DB Trigger — Signup Credits

Function handle_new_user() fires on INSERT into auth.users. Inserts a row into public.credits with balance = 3. This is how every new user gets their 3 free credits automatically on signup.
